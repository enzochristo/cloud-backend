Relatório de Testes de Carga — Demay Bank

Disciplina: Computação em Nuvem — Primeiro Semestre de 2026

Ferramenta: Apache JMeter 5.6.3

Data de execução: 30 de maio de 2026

Duração total do teste: ~21 segundos

Total de requisições: 6.400

1. Introdução

Este relatório apresenta os resultados dos testes de carga realizados sobre a plataforma Demay Bank, uma API financeira distribuída hospedada na AWS. O objetivo foi validar a robustez da arquitetura sob cenários de uso intenso, incluindo criação de transações em alta escala, consultas simultâneas, rajadas de requisições e avaliação do fluxo assíncrono mediado por filas SQS.

Os testes foram executados a partir de uma máquina local contra os endpoints de produção da aplicação, sem nenhuma alteração na infraestrutura, garantindo que os resultados refletem o comportamento real do sistema em ambiente AWS.

2. Arquitetura Sob Teste

A plataforma é composta por dois fluxos principais:

Fluxo ECS (via ALB):

Cliente → ALB → ECS (NestJS) → RDS PostgreSQL

Responsável por: cadastro de usuários, login e listagem.

Fluxo assíncrono (via API Gateway):

Cliente → API Gateway → Lambda 1 (validação) → SQS → Lambda 2 (processamento) → RDS PostgreSQL

Responsável por: criação e processamento de transações financeiras.

5. Análise por Cenário

5.1 Health Check (Baseline)

APDEX 1,000 — 0% de erro — latência média de 159ms. Desempenho perfeito em 500 requisições. Estabelece o baseline da infraestrutura: ALB distribuindo corretamente, ECS respondendo de forma consistente.

5.2 Registro de Usuários em Alta Escala

99% de erro — mas não é falha de infraestrutura. Os 100 usuários virtuais tentaram registrar e-mails já existentes no banco, recebendo corretamente HTTP 409 (Conflict). A latência média de 831ms demonstra que as requisições chegaram, foram processadas pelo NestJS, consultaram o RDS e retornaram a resposta adequada.

5.3 Login Simultâneo

APDEX 0,601 — 0,40% de erro — latência média de 867ms. 50 usuários simultâneos realizaram 500 autenticações. Apenas 2 falhas por timeout pontual. Sistema suportou bem a carga de autenticação concorrente.

5.4 Criação de Transações em Alta Escala

0% de erro em 1.000 requisições. Este é o resultado mais crítico do teste. 100 usuários simultâneos dispararam transações contra API Gateway → Lambda 1 → SQS sem nenhuma falha técnica.

A latência média de 963ms é justificada pelo fluxo: API Gateway + inicialização da Lambda (possível cold start) + consulta ao Secrets Manager + validação no RDS + enfileiramento no SQS. O percentil 99 de 2.926ms indica que mesmo nas condições mais adversas o sistema respondeu em menos de 3 segundos.

5.5 Consulta de Status Simultânea

APDEX 0,698 — 0% de erro — latência média de 680ms. 150 usuários simultâneos realizaram 3.000 consultas. O maior volume do teste. O RDS respondeu a todas sem erros. Mediana de 330ms indica que a maioria das requisições foi rápida.

5.6 Rajada (Burst / Spike Test)

0% de erro com 300 threads em 2 segundos. Mesmo sob pico extremo, o sistema não retornou nenhum erro técnico.

A latência média de 2.504ms e percentil 99 de 9.305ms revelam degradação esperada no cenário de estresse. A Lambda escalonou automaticamente, o SQS absorveu todas as mensagens — demonstrando o principal benefício da arquitetura serverless com filas: resiliência natural a picos de carga.

6. Validação do Fluxo Assíncrono

A validação mais importante não está nos números do JMeter, mas na evidência direta no banco de dados. Após a execução completa dos testes:

SELECT status, COUNT(*) FROM Transfer GROUP BY status;

Figura 3 — Consulta ao RDS PostgreSQL confirmando 1.907 transações completed e 5 refused após os testes

1.907 transações processadas com sucesso de ponta a ponta. O fluxo completo funcionou: JMeter → API Gateway → Lambda 1 → SQS → Lambda 2 → RDS. Nenhuma mensagem foi perdida na fila SQS.

As 5 transações refused correspondem a casos de saldo insuficiente — comportamento correto de regra de negócio, não falha técnica.

7. Análise Crítica

Pontos Fortes

  • Resiliência sob carga: 0% de erro técnico nos endpoints de transação, mesmo no burst com 300 threads.
  • Escalabilidade automática da Lambda: Sem configuração manual, a Lambda 1 escalonou para processar requisições em paralelo durante o spike.
  • Confiabilidade do SQS: 100% das mensagens enfileiradas foram processadas, sem perda ou duplicidade.
  • Estabilidade do RDS: Respondeu a todas as consultas de leitura sem erros mesmo com 150 threads simultâneas.

Pontos de Atenção

  • Cold start da Lambda: Latência média de 963ms no fluxo de transações vs. 159ms no ECS. Provisioned Concurrency reduziria este overhead em produção real.
  • Degradação no burst: Percentil 99 de 9.305ms pode ser inaceitável para um produto financeiro real. Throttling no API Gateway e autoscaling mais agressivo seriam recomendados.
  • Gargalo de leitura: GET /user com 150 threads apresentou máximo de 7.923ms. Para escala maior, uma read replica ou camada de cache (ElastiCache) seria recomendada.

8. Conclusão

Os testes de carga confirmam que a arquitetura da plataforma Demay Bank é robusta e funcional para os cenários propostos. Os principais objetivos foram atingidos:

  • O fluxo assíncrono Lambda → SQS → Lambda funcionou com 100% de confiabilidade (1.907 transações completadas, 0 perdidas)
  • O sistema suportou 309 requisições por segundo de throughput sustentado
  • Nenhum erro técnico ocorreu nos endpoints de transação, nem no cenário de burst extremo
  • Taxa de sucesso global de 92,23% — os 7,77% de falha são integralmente explicados por rejeição de e-mails duplicados (HTTP 409), não por falha de infraestrutura

A arquitetura demonstrou os benefícios práticos do modelo distribuído em nuvem: escalabilidade automática via Lambda, desacoplamento via SQS e persistência confiável via RDS PostgreSQL.
